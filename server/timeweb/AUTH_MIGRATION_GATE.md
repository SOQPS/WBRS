# Вход пользователей при переезде CLRS на Timeweb

Статус на 2026-09-30: **проектное решение, не внедрённый вход на Timeweb**. Новые платные ресурсы не заказывались; хеши паролей и персональные данные для этой проверки не выгружались.

## Рекомендуемый первый этап: оставить Firebase Authentication

Приложение уже выполняет вход и регистрацию по email/паролю через Firebase (`lib/service/auth_service.dart`), а сброс пароля — через Firebase на экране входа. После успешного входа клиент может передавать Firebase ID token по HTTPS в API на Timeweb. API проверяет подпись, срок действия, `aud`/`iss` проекта `chatapp-4e347` и использует `sub` как прежний UID. Данные приложения при этом могут обслуживаться Timeweb; пользователям не потребуется менять пароль. Это [официально описанный сценарий собственного backend](https://firebase.google.com/docs/auth/admin/verify-id-tokens). Firebase Auth, регистрация, восстановление пароля и выдача/обновление токенов продолжат работать в исходном проекте; его нельзя отключить после переноса данных.

В каталоге уже есть `api/firebase-id-token.mjs` с проверкой ID token по открытым ключам Google и синтетическими тестами. **Но `api/server.mjs` пока обслуживает лишь `/healthz` и `/readyz`; защищённых маршрутов CLRS и подключения этой проверки к ним нет.** Проверка JWT сама по себе не сообщает, был ли пользователь затем заблокирован или его сеанс отозван: [Firebase прямо указывает на отдельную проверку revocation](https://firebase.google.com/docs/auth/admin/manage-sessions). Перед выпуском API нужны серверные права на каждое действие, связь UID с профилем/ролью в новой БД, политика для удалённых/отключённых аккаунтов и отозванных токенов, затем проверка входа, выхода, смены аккаунта и сброса пароля на тестовых пользователях. Текущий локальный verifier эту задачу ещё не закрывает.

Owner ADC, применённый для инвентаризации, нужен только локальному оператору. Проверка подписи через публичные ключи не требует хранить Owner ADC, пароль или сервисный ключ на Timeweb; если для немедленной проверки отзыва/статуса потребуется обращение к Firebase Auth, следует отдельно спроектировать ограниченную серверную идентичность или безопасную синхронизацию статусов. Owner ADC на Timeweb не размещать.

## Если позже потребуется полностью уйти с Firebase Auth

Обычный список пользователей **не переносит пароли**. Действующий `auth-rest.mjs` намеренно удаляет `passwordHash`, `salt` и версию из ответа перед сохранением; `EXPORT_PREPARATION.md` прямо исключает их из архива. Пароли в открытом виде получить нельзя. По [Firebase Admin `listUsers`](https://firebase.google.com/docs/auth/admin/manage-users#password_hashes_of_listed_users) и [REST `accounts:batchGet`](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/batchGet), для чтения UID/метаданных нужно `firebaseauth.users.get`, а для выдачи `passwordHash`/`passwordSalt`/версии сверх того — `firebaseauth.configs.getHashConfig`; без второго разрешения поля скрываются. Нужен OAuth scope `identitytoolkit`, `firebase` или `cloud-platform` для `batchGet`. Роль `roles/firebaseauth.viewer` даёт `users.get` и `configs.get`, **но не** `configs.getHashConfig`; подтверждённая роль Owner содержит последнее разрешение. Для отдельного миграционного субъекта Firebase рекомендует временную custom IAM role с точным `firebaseauth.configs.getHashConfig`, а не широкую роль Editor. Наличие разрешения у Owner не означает, что текущий безопасный экспортёр выгрузил хеши: он этого не делает.

Кроме индивидуальных hash/salt нужен чувствительный `hashConfig` проекта: алгоритм, `signerKey`, `saltSeparator`, `rounds`, `memoryCost` (для Firebase `SCRYPT`; проверить фактическое значение в проекте). Чтение [конфигурации проекта через REST](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/projects/getConfig) требует `firebaseauth.configs.get`; возврат секретных параметров дополнительно ограничен `firebaseauth.configs.getHashConfig`. [Firebase CLI описывает эти параметры](https://firebase.google.com/docs/cli/auth#password_hash_parameters) и различие между модифицированным Firebase `SCRYPT` и стандартным `STANDARD_SCRYPT`. [Документация HashConfig](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/projects.tenants#HashConfig) также указывает, что разные аккаунты могут иметь разные версии алгоритма. [Firebase `auth:export`](https://firebase.google.com/docs/cli/auth#authexport) предупреждает: аккаунты с импортированными ранее алгоритмами, ещё не перехешированные Firebase после входа, могут выйти с пустыми hash/salt. Поэтому один подсчёт провайдера `password` не доказывает переносимость всех паролей.

Для собственной авторизации на Timeweb потребуются защищённое хранение hash/salt/параметров, реализация и проверка **именно фактических** алгоритмов и версий на контролируемых тестовых аккаунтах, сохранение UID и флагов учётной записи, собственные сессии, лимиты попыток входа, сброс пароля и синхронизация изменений до финального переключения. Экспорт и импорт этих секретов допустимы только в отдельном защищённом контуре, после подтверждения поддержки алгоритмов целевой системой; сам `firebase auth:import` импортирует учётные записи **в Firebase**, а не в MySQL/Timeweb. Пока такой сквозной тест не пройден, обещать вход со старым паролем без Firebase нельзя. Для неподдерживаемых записей нужен согласованный сценарий смены пароля.

Инвентаризация `ACCOUNT_INVENTORY.md` за 2026-09-30 зафиксировала 8 202 учётные записи с провайдером `password`, без выгрузки личных данных или хешей. Это подтверждает масштаб задачи, но не покрытие паролей и не работоспособность нового входа.
