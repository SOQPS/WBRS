# Шаблон отдельного тестового контура CLRS на Timeweb

**Статус: подготовка, не развёрнуто.** Новый VPS, PostgreSQL и приватные S3-бакеты не заказаны: владелец просил обойтись без новых платных ресурсов. На существующем MySQL `LRS` создана только пустая `clrs_staging`. Команды ниже для отдельного PostgreSQL/VPS — альтернативный план на случай согласованного расширения инфраструктуры; MySQL-скрипты ниже готовят резервирование существующей staging-базы. Ни один вариант ещё не обслуживает CLRS. Контур нельзя объявлять рабочим до тестовой миграции и проверки сценариев из [PLAN.md](../PLAN.md).

## До запуска

1. Создать **новый** VPS с Docker Engine + Compose plugin и доступом по отдельному SSH-ключу. Открыть снаружи только 80/443 и ограниченный SSH. Создать отдельный управляемый PostgreSQL в приватной сети; новый database/user для CLRS, отдельный read-only пользователь для дампов и отдельный пользователь, который может восстанавливать **только тестовую БД**. Не использовать существующий MySQL `default_db`.
2. Создать два **приватных** S3-бакета с версионированием: для пользовательских файлов и для резервных копий. Дать API доступ только к первому, сервису бэкапов — запись только во второй. Настроить хранение версий/сроки хранения и независимую внешнюю копию: один бакет того же провайдера не защищает от потери всего аккаунта. Нужна отдельная процедура проверки восстановления фотографий из версий или внешней копии.
3. Направить новый DNS-адрес только на новый VPS. Caddy выпустит HTTPS-сертификат после доступности DNS и портов 80/443. Новый API-образ должен слушать порт 8080; `GET /healthz` показывает лишь работоспособность процесса, а `GET /readyz` возвращает 200 только при готовности зависимостей, в том числе БД. Один успешный `readyz` не подтверждает работу маршрутов CLRS, прав доступа и S3: их проверяют отдельно. Эти файлы не реализуют API или контракт клиента.
4. Скопировать этот каталог на VPS в `/opt/clrs/deploy`. Создать вне git `/etc/clrs-staging/compose.env` и `/etc/clrs-staging/api.env` по примерам: владелец root, права `0600`. Указать подлинный SHA-256 digest проверенного API-образа; использовать отдельные свежие ключи БД, S3 и сессий. Логин/пароль панели Timeweb сюда не записывать. Ввести реальные адреса Timeweb и CA-сертификат выбранной БД, не брать адреса `.example.invalid` из шаблонов. Путь `CLRS_DATABASE_CA_HOST_FILE` указывает на публичный CA-файл VPS (например, `root:root 0644`); Compose монтирует его только для чтения как `/run/secrets/database-ca.pem`, и API получает этот путь через `DATABASE_CA_FILE`.

## Выпуск и возврат образа

`release.sh` по умолчанию показывает план. Развёртывание требует точного digest образа и повторного указания его при выполнении:

```sh
sudo /opt/clrs/deploy/release.sh plan registry.example.invalid/clrs/api@sha256:...
sudo /opt/clrs/deploy/release.sh deploy registry.example.invalid/clrs/api@sha256:... --execute --confirm-image registry.example.invalid/clrs/api@sha256:...
sudo /opt/clrs/deploy/release.sh rollback
sudo /opt/clrs/deploy/release.sh rollback --execute --confirm-image registry.example.invalid/clrs/api@sha256:...
```

Скрипт проверяет конфигурацию Docker Compose, запускает только новый стек, ждёт HTTPS `/readyz`, хранит digest предыдущего исправного образа в `/var/lib/clrs-staging` и при неуспехе пытается вернуть его. При откате уже скачанный образ используется без обращения к реестру. Восстановление **образа API** не откатывает записи в БД. После реального переключения с Firebase возврат пользователей к Firebase требует отдельного окна синхронизации и разбора записей, сделанных после переключения; см. `PLAN.md`.

## Резервная копия PostgreSQL

На VPS установить `postgresql-client`, `age`, `awscli`, `openssl`. Создать `/etc/clrs-staging/backup.env` по примеру, CA-файл и **публичный** age-recipient; закрытый ключ age хранить вне VPS. Создать системного пользователя `clrs-backup`; файл `backup.env` — `root:clrs-backup 0640`, каталог `/var/backups/clrs-staging` — `clrs-backup:clrs-backup 0700`. S3-ключу нужны запись нового объекта и чтение для сверки байтов, но не удаление; endpoint должен использовать HTTPS. Сначала проверить план без чтения БД и записи в S3, затем один ручной запуск:

```sh
sudo -u clrs-backup /opt/clrs/deploy/backup.sh
sudo -u clrs-backup /opt/clrs/deploy/backup.sh --execute
```

Скрипт передаёт `pg_dump -Fc` сразу в `age`; незашифрованный дамп не появляется на диске. Он сравнивает размер, SHA-256 metadata и SHA-256 реально скачанных байтов загруженного объекта. После успешной проверки локальный зашифрованный файл удаляется; при неудаче загрузки/проверки он остаётся для ручного повтора. Это подтверждает передачу, **но не восстановимость данных**: её проверяет отдельная пробная операция ниже. После ручной проверки установить unit-файлы в `/etc/systemd/system/`, затем включить `clrs-pg-backup.timer`. Настроить мониторинг оставшихся после ошибок файлов и свободного места; политику хранения S3-копий задать отдельно после расчёта объёма и стоимости.

## Отдельная резервная копия MySQL 8.4 `clrs_staging`

Для уже созданной MySQL `clrs_staging` предусмотрены отдельные `backup-mysql84.sh` и `restore-mysql84.sh`. Они не используют PostgreSQL-скрипты, `default_db`, Firebase или S3 и не создают услугу Timeweb. На машине запуска нужны клиент MySQL 8.4 (`mysqldump`/`mysql`), `age` и `openssl`. Скопировать `mysql-backup.env.example` и `mysql-restore.env.example` во **внешние** `/etc/clrs-staging/mysql-backup.env` и `/etc/clrs-staging/mysql-restore.env` с правами `0600`; пароль не передавать в аргументах команд. Дать каждому отдельному пользователю права только на `clrs_staging.*`; пользователю копирования — чтение, пользователю восстановления — необходимые права на создание и заполнение таблиц. Подключение использует проверку CA и DNS-имени сервера (`VERIFY_IDENTITY`); приватный CA-файл должен соответствовать серверу Timeweb.

Подготовить каталог `/var/backups/clrs-staging` с владельцем, запускающим копирование, и правами `0700`. Публичный age-recipient хранить в указанном env путём; закрытый age-ключ держать на доверенной машине восстановления вне VPS. Проверить настройки, затем явно запустить копирование:

```sh
/opt/clrs/deploy/backup-mysql84.sh
/opt/clrs/deploy/backup-mysql84.sh --execute
```

`mysqldump` читает только явно названную `clrs_staging` через одну InnoDB-транзакцию и передаёт SQL напрямую в `age`. На диске остаются только зашифрованный `.sql.age` и его `.sha256`; архив необходимо отдельно перенести в независимое защищённое хранилище. Это локальная подготовка резервной копии, а не проверенная защита от потери VPS/аккаунта. Во время дампа нельзя менять структуру таблиц; для не-InnoDB таблиц согласованность снимка отдельно не доказана.

Для восстановления скопировать оба файла архива и checksum на доверенную машину, создать **пустую** `clrs_staging` и предоставить отдельному пользователю права только на неё. Настроить `mysql-restore.env` и приватный age-ключ (`0600`). Сначала скрипт сверяет SHA-256, полностью расшифровывает архив без сохранения SQL на диск, проверяет его маркер `clrs_staging` и пустоту целевой базы. Выполнение требует точного имени дважды:

```sh
/opt/clrs/deploy/restore-mysql84.sh --archive /secure/clrs_staging-YYYYMMDDTHHMMSSZ-ID.sql.age --target-db clrs_staging
/opt/clrs/deploy/restore-mysql84.sh --archive /secure/clrs_staging-YYYYMMDDTHHMMSSZ-ID.sql.age --target-db clrs_staging --execute --confirm-target clrs_staging
```

Копировать `.sha256` рядом с архивом, сохраняя то же имя с суффиксом `.sha256`. SHA-256 обнаруживает повреждение, но сам по себе не доказывает происхождение архива: получать его только из доверенного хранилища. MySQL фиксирует DDL по отдельным инструкциям. При ошибке восстановления возможны частично созданные таблицы; перед повтором проверить состояние и вновь подготовить пустую базу. После успешного запуска сверить схему, строки и связи с записанным составом исходного снимка. Эти команды пока проверены только синтетическими клиентами, без подключения к Timeweb.

Фотографии и вложения копируются отдельно. Создать `/etc/clrs-staging/media-backup.env` по примеру с ключом, который читает бакет файлов и пишет только в бакет резервных копий. Указать ID **именно целевого** бакета в `BACKUP_S3_BUCKET_ID` и отдельный токен Timeweb, которому достаточно читать его настройки, в `TIMEWEB_API_TOKEN`; значения хранить только вне git. На машине запуска нужны Node.js 22, зависимости каталога `server/timeweb` (`npm ci`) и AWS CLI. `backup-media.sh` перед копированием проверяет включённое версионирование обоих бакетов, тип `private`, ACL и отсутствие публичной policy у целевого бакета, а затем повторяет проверку приватности после копирования. Проверка приватности не делает пробной записи. Скрипт никогда не применяет `--delete`. По умолчанию он не обращается к S3:

```sh
/opt/clrs/deploy/backup-media.sh
/opt/clrs/deploy/backup-media.sh --execute
```

Первую копию запустить вручную после оценки числа файлов и стоимости S3 операций. Этот скрипт копирует текущие версии объектов; история старых версий и согласованный снимок во времени не создаются. До признания файловой копии пригодной для переноса нужны заморозка изменений или манифест конкретных версий объектов, затем сверка всех файлов и пробное восстановление. Историю старых версий надо сохранять политикой бакетов или отдельной внешней копией. По одному успешному `sync` нельзя заключать, что восстановление проверено.

## Пробное восстановление

Скачать один `.dump.age` из бакета резервных копий на доверенную машину. Создать **новую пустую** PostgreSQL database с именем `clrs_restore_*` и доступом пользователя `clrs_restore` только к ней. Закрытый age-ключ и `/etc/clrs-staging/restore.env` держать вне VPS и git; права каждого файла `0600`. Скрипт сначала проверяет расшифровку/формат и пустоту цели, не внося изменений. Выполнение требует явного подтверждения имени:

```sh
/opt/clrs/deploy/restore.sh --archive /secure/backup.dump.age --target-db clrs_restore_qa
/opt/clrs/deploy/restore.sh --archive /secure/backup.dump.age --target-db clrs_restore_qa --execute --confirm-target clrs_restore_qa
```

Восстановление идёт одной транзакцией без подмены владельцев. После него отдельно сравнить таблицы, количество записей и связи с исходным снимком. Для проверки файлов создать **новый пустой** приватный бакет `clrs-restore-*` и `/etc/clrs-staging/media-restore.env` с отдельным ключом, который читает бэкап и пишет только в этот бакет. Указать точный `RESTORE_S3_BUCKET_ID` и read-only `TIMEWEB_API_TOKEN` для проверки настроек; нужны те же Node.js 22 и зависимости. Скрипт проверит приватность целевого бакета до и после копирования. Затем:

```sh
/opt/clrs/deploy/restore-media.sh --target-bucket clrs-restore-qa
/opt/clrs/deploy/restore-media.sh --target-bucket clrs-restore-qa --execute --confirm-target clrs-restore-qa
```

После копирования сравнить байты и контрольные суммы выборки файлов и проверить, что тестовый бакет закрыт от посторонних. Ни один из этих тестов не должен писать в Firebase или старый MySQL.

Проверка шаблонов без доступа к облаку: `bash -n backup.sh restore.sh backup-mysql84.sh restore-mysql84.sh backup-media.sh restore-media.sh release.sh`, `python3 test_mysql84_backup_restore.py`, `python3 test_media_privacy.py` и `node --test check-private-media-bucket.test.mjs`. На VPS дополнительно: `docker compose --env-file /etc/clrs-staging/compose.env -f compose.yaml config --quiet`, затем реальный HTTPS-`/readyz`, проверка маршрутов и восстановление тестового дампа. До появления API-образа и ресурсов эту проверку провести нельзя.
