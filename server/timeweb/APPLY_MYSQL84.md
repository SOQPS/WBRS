# Однократное применение схемы MySQL 8.4

Реальный запуск 2026-09-30 выполнен успешно один раз. Перед DDL проверены
точные пять прав на `clrs_staging.*`, отказ в `default_db`, проверенный TLS,
MySQL 8.4.4-4, размер страницы 16384 и пустая схема. Чтение после применения
подтвердило 42 таблицы, 66 FK, version 1, event counter 0 и нулевые данные
во всех рабочих/архивных таблицах. Приватный журнал завершён со статусом
`applied_verified`; повторное применение к этой базе запрещено.

`apply-mysql84-schema.mjs` применяет только проверенную версию
`db/001_initial_mysql84.sql` с SHA-256
`069cc1a473475a85742c71387374da44ca5483abd219c00affb9cc9ce739f621`.
Проверки: строго CREATE, REFERENCES, SELECT, INSERT, UPDATE только на
`clrs_staging.*`; global USAGE без иных глобальных прав; отказ в доступе
к `default_db`; TLS с проверкой CA и DNS-имени; MySQL 8.4, InnoDB 16 KiB,
utf8mb4 и строгий SQL-режим; отсутствие таблиц, views, routines, triggers, events.
Строгий SQL-режим устанавливается только для своего соединения, поскольку
действующая Timeweb конфигурация не включает его по умолчанию. Глобальные
настройки сервера не изменяются.

JSON с реквизитами (`host`, `port`, `user`, `password`, `database`) и сертификат
CA должны находиться вне репозитория с правами `0600`. Значения пароля CLI
не принимает. Сначала только проверить:

```sh
node apply-mysql84-schema.mjs \
  --config-file /private/mysql.json --ca-file /private/timeweb-ca.crt \
  --mode check --confirm-target-db clrs_staging
```

После успешной проверки выполнить однократно:

```sh
node apply-mysql84-schema.mjs \
  --config-file /private/mysql.json --ca-file /private/timeweb-ca.crt \
  --mode apply --confirm-target-db clrs_staging \
  --backup-file /private/clrs-empty-before-schema.json
```

Перед первым DDL создаётся новый эксклюзивный файл `0600`: снимок пустой
схемы и журнал. Существующий файл не перезаписывается. Журнал содержит только
состояние и номер операции, счётчики и код ошибки; реквизитов и данных
пользователей в нём нет. После применения проверяются 42 ожидаемые таблицы,
66 внешних ключей, маркер версии 1, event counter 0 и отсутствие данных
во всех остальных таблицах.

MySQL DDL фиксируется автоматически, поэтому скрипт останавливается на
первой ошибке и не пытается повторить или удалить уже созданные таблицы.
При ошибке нужно проверить приватный журнал и фактическую схему вручную.
Непустую целевую схему скрипт всегда отклоняет. Это подготовка структуры,
а не перенос пользователей или включение нового приложения.

Подготовленный `import-clrsx2-mysql84.mjs` сохраняет полные исходные Auth,
Firestore и Storage записи в `legacy_*`, включая дочерние документы без
существующего родителя; завершённость источника проверяется до сети.
Импорт отвергает `completeSource: false`, неверный источник, неполный
или повреждённый зашифрованный архив. На вход нужно подавать полный
подтверждённый CLRSX2 архив; текущую частичную выгрузку использовать нельзя.
Файлы записываются только в проверенный приватный S3 bucket. При сопоставлении
с рабочими таблицами нельзя автоматически удалять сиротские записи,
назначать им выдуманных родителей или менять UID.

Полное выключение Firebase Auth дополнительно требует отдельного защищённого
экспорта password hash/salt и hashConfig. Нынешний архив намеренно этих
секретов не содержит. Проверка входа через временный Firebase ID token
не подтверждает самостоятельную авторизацию Timeweb со старым паролем.
Подробные разрешения и проверка алгоритмов: `AUTH_MIGRATION_GATE.md`.
