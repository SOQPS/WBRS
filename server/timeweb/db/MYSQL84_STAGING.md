# CLRS: отдельная схема для MySQL 8.4 на Timeweb

**Статус на 2026-09-30:** схема применена один раз в действующем Timeweb MySQL 8.4.4-4, база `clrs_staging` существующего кластера LRS. Реальная проверка подтвердила 42 ожидаемые таблицы InnoDB/utf8mb4, 66 внешних ключей, маркер версии 1, event counter 0 и отсутствие пользовательских/архивных данных во всех таблицах. `default_db` не менялась. Новых платных ресурсов нет. Пользователь `clrs_migrate` имеет строго CREATE, REFERENCES, SELECT, INSERT, UPDATE на `clrs_staging.*`, доступ к `default_db` отклонён. Для `clrs_api_ro` независимо проверены SELECT только на этой базе, отказ в `default_db` и TLS с проверкой CA и DNS-имени.

Применённый [SQL](001_initial_mysql84.sql) закреплён SHA-256 `069cc1a473475a85742c71387374da44ca5483abd219c00affb9cc9ce739f621`; он не создаёт новую базу, не содержит пользователей, паролей, грантов или реальных данных. Исходная [PostgreSQL-схема](001_initial.sql) остаётся отдельной. Приватный журнал пустой схемы/DDL сохранён локально с правами `0600`, вне Git. Код и порядок запуска: [APPLY_MYSQL84.md](../APPLY_MYSQL84.md). Схема подготовлена; перенос реальных данных и работа приложения на ней ещё не подтверждены.

## Локальная проверка

Из каталога проекта `CLRS`:

```sh
python3 server/timeweb/db/validate_mysql84_schema.py
```

Скрипт работает только с двумя локальными SQL-файлами: сверяет 42 таблицы, исходные поля и 66 связей, а также отсутствие команд для другой базы. Он не подключается к Timeweb/Firebase/S3. Полноценное исполнение и чтение обратно отдельно проверены на Timeweb MySQL 8.4.4-4 через `apply-mysql84-schema.mjs`.

## Выполненные проверки перед применением

1. Владелец включил TLS 2026-09-30. Для применения схемы/импорта предоставить отдельному пользователю минимальные необходимые права только на `clrs_staging.*`; SELECT-only пользователь API для записи не подходит; держать пароль и TLS-настройки вне репозитория и командной строки. Не использовать старую `default_db` или пользователя Flask-приложения.
2. Прочитать в панели/клиенте `SELECT VERSION(), @@innodb_page_size;` и убедиться, что сервер — MySQL 8.4, размер страницы InnoDB — **16384 байта**, а `SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='clrs_staging';` возвращает **0**. Схема рассчитана на 16-КБ страницы и ключи до 3072 байт.
3. Защищённый CLI сохранил новый приватный журнал состояния пустой базы и применил закреплённый SQL **один раз**, последовательно, через TLS с проверкой CA/DNS. Пароль прочитан из файла `0600`, без передачи в командной строке. В своём соединении включён `STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION`; глобальный SQL-режим не изменялся.
4. Запустить только читающий [verify_empty_mysql84.sql](verify_empty_mysql84.sql) тем же способом до импорта. Ожидаются 42 таблицы, 66 внешних ключей, одна отметка версии, одна строка счётчика и нули в четырёх таблицах пользовательских данных. При другом результате остановиться и выяснить причину.

MySQL фиксирует DDL по отдельным инструкциям. Если применение прервётся, часть таблиц может остаться, а отметки версии не будет. Не запускать файл повторно поверх такого состояния: сначала сверить объекты и восстановить заведомо пустую `clrs_staging` по согласованной процедуре.

## Правила будущего импорта

- `legacy_auth_users`, `legacy_documents` и `legacy_storage_objects` сохраняют исходные UID, полные пути, типизированный JSON, времена, размеры, метаданные и SHA-256. В них намеренно нет связи с родительским документом: вложенная запись без родителя должна сохраниться и попасть в отчёт. Длинные пути индексируются по SHA-256; импортёр обязан сверять **полное исходное значение** при совпадении хеша и останавливать конфликт, а не заменять путь.
- В предметных таблицах ID ограничены 191 символом для точных внешних ключей и индексов MySQL. Если исходный ID длиннее, его запись остаётся в `legacy_*`, а продвижение останавливается до отдельного решения; обрезать ID нельзя. Приложение/импортёр должны работать в строгом SQL-режиме и в UTC (`DATETIME(6)` не хранит часовой пояс). Тип исходной метки времени остаётся в типизированном JSON.
- MySQL проверяет внешние ключи сразу. Сначала нужны аккаунты, участники чата/встречи и родительские комментарии/сообщения; для ссылок вперёд потребуется двухэтапное заполнение допустимых nullable-полей. Частичные индексы PostgreSQL заменены индексами с полями состояния и nullable-уникальностью; «одно основное фото» контролирует вычисляемый `primary_slot`.
- Отдельный сервис должен ограничить доступ к `auth_credentials`, токенам устройств, исходным архивам и колбэкам оплаты. Схема не реализует проверку прав API, транзакции баланса/реестра, синхронизацию медиа, вход по старому паролю или сверку реальных пользователей.

Локальные [MySQL CLI, адаптер импорта и чтения обратно](../IMPORT_MYSQL84.md) для `legacy_*` уже подготовлены, но ещё не запускались против MySQL/S3 Timeweb. Их pinned connection теперь явно устанавливает строгий SQL-режим перед транзакцией. PostgreSQL CLI `import-clrsx2.mjs` остаётся отдельным. До переключения нужны приватный S3, реальный проверенный импорт, контроль приватности объектов, полноценный API, проверка сценариев приложения и план отката.
