# Старые пароли CLRS: серверная совместимость и хранение

Статус 2026-09-30: серверные модули подготовлены и локально проверены;
**собственный вход через развернутый Timeweb ещё не работает**.
Новых платных ресурсов, изменений паролей или повторной выгрузки Firestore нет.

`api/firebase-scrypt.mjs` реализует фактический модифицированный Firebase SCRYPT:
salt пользователя объединяется с salt separator, scrypt получает `N=2^memoryCost`,
`r=rounds`, `p=1` и выводит 64 байта; первые 32 байта служат ключом AES-256-CTR
с нулевым начальным счётчиком, который шифрует signer key проекта. Сравнение
с сохранённым hash выполняется через `timingSafeEqual`. Это соответствует
[официальной реализации Firebase](https://github.com/firebase/scrypt/blob/master/lib/scryptenc/scryptenc.c)
и проверено на [публичном эталонном примере Firebase](https://github.com/firebase/scrypt#password-hashing).
Пример не содержит пользователей или паролей CLRS.

Поддержка намеренно ограничена `SCRYPT`, версиями `0` и `"0"` с сохранением
исходного типа. Другой алгоритм, версия, недоступные/скрытые материалы,
некорректная кодировка или превышение лимита KDF отклоняются. Оригинал
остаётся в зашифрованном архиве и не заменяется случайным новым паролем.
Работа KDF асинхронная, ограничена 64 MiB на одну операцию и двумя
параллельными операциями по умолчанию; переполнение возвращает безопасный
код `KDF_BUSY`. Пароль не обрезается и не нормализуется; предел входа —
4096 байт UTF-8. Этот лимит не заменяет лимит попыток входа на сервере.

`auth-credential-storage.mjs` использует уже созданную `auth_credentials` без
дополнительного DDL. Hash и salt хранятся как AES-256-GCM ciphertext в двух
BLOB; UID, версия, статусы, провайдеры и идентификатор конфигурации связаны
с ciphertext через authenticated data. Порядок ключей MySQL JSON может
измениться при сохранении: проверка использует фиксированный порядок полей
и прошла отдельный тест этой особенности. Паддинг и URL-safe кодировка
исходных hash/salt сохраняются точно.

В `parameters` есть `material_format=aes256gcm-v1`, `config_ref` и fingerprint
конфигурации, исходная версия и статусы; **signer key там отсутствует**.
Для работы нужны два отдельных секрета backend: конфигурация Firebase SCRYPT
из защищённого credential export и новый случайный 32-byte wrapping key.
Они размещаются в закрытых env/secrets или файлах `0600`, отдельно от БД,
Git, APK, резервных копий БД и пользовательских отчётов. Потеря wrapping key
делает строки непригодными для входа: его резервная копия обязательна.
Owner ADC на сервер не переносится.

Адаптер требует одно фиксированное соединение, созданное через `mysql84Config`
с CA, проверкой имени DNS и сертификата. Режим по умолчанию — только чтение.
Запись требует явного `readOnly:false`, точных миграционных прав и отказа
доступа к `default_db`; все запросы направлены в `clrs_staging`. Он не создаёт
аккаунты, не меняет email, lifecycle, роли или пароли. Перед вставкой UID
должен уже существовать в `accounts`, а disabled/email_verified должны
совпадать с импортированным источником. Существующая запись проверяется
полным readback; конфликт отклоняется без перезаписи. Транзакцию завершает
вызывающий importer; при ошибке нужен rollback и сверка результата.

## Что проверено

- 9 адресных локальных тестов: официальный правильный/неправильный пароль,
  отключённый аккаунт, неизвестные версии, предел памяти и параллелизма,
  tampering, чужой UID/ключ/конфигурация, запрет входа текущему заблокированному,
  удалённому или отключённому аккаунту, MySQL JSON reorder, запрет записи
  в read-only и неправильную БД, отсутствие перезаписи конфликта.
- Локальный проход по настоящему зашифрованному архиву всех 8208 аккаунтов:
  8208 поддержанных структур и 8208 полных encrypted-row roundtrip,
  неподдержанных структур 0. Сохранены UID, тип версии, hash/salt, статусы
  и провайдеры; открытые данные не записывались в отчёт.
- Реальных записей в MySQL/Firebase в этом проходе: 0. Настоящий пароль
  какого-либо аккаунта CLRS не использовался и не получался.

## Что требуется до переключения

Нужны импорт `accounts`/идентичностей из полного проверенного архива,
защищённый импорт credential rows, собственные login/session/refresh/logout
маршруты, блокировка по текущему `accounts.lifecycle`/`disabled`, лимиты
попыток, отзыв сессий и восстановление пароля. Затем требуется живой вход
контролируемого пользователя через Timeweb и мобильный клиент, включая
неправильный пароль, смену аккаунта и выход. Перед финальным переключением
нужна синхронизация изменений Firebase после снимка. Прохождение эталонного
теста и roundtrip не закрывает эти пользовательские сценарии.
