# CLRS: доверенная отправка push и участники обсуждения (E470)

**Статус: подготовлено и проверено локально; не развёрнуто, реальный FCM не вызывался.** Пакет переиспользует установленные Firebase Admin/Functions SDK. AWS, Timeweb, новые зависимости и ключи в APK для push не нужны. Существующая функция перевода не изменена. Никакие облачные ресурсы этой работой не создавались.

## Экспортируемые функции

| Функция | Источник |
| --- | --- |
| `requestPush` | HTTPS POST после сохранения сообщения |
| `pushPrivateMessage` | Создание `chats/{room}/chats/{message}` |
| `pushMeetingMessage` | Создание `meets/{meeting}/messages/{message}` |
| `notifyPostComment` | Создание `posts/{post}/comments/{comment}` |
| `notifyPostLike` | Создание `posts/{post}/likes/{uid}` |
| `notifyCommentLike` | Создание `posts/{post}/comments/{comment}/likes/{uid}` |
| `notifyFriendRequest` | Создание `users/{recipient}/friend_requests/{sender}` |
| `notifyFriendAccepted` | Создание `users/{requester}/friends/{accepter}` |
| `notifyRegionalMeeting` | Создание публичной `meets/{meeting}` в регионе получателя |

Триггеры работают после подтверждённой записи, даже если приложение уже закрыто. HTTP — дополнительный путь с тем же ключом дедупликации. Клиентский composer больше не ждёт вспомогательный push. Старая gift-операция без messageId не отправляет некорректный HTTP: подарок обрабатывается по реальной записи чата; сопутствующая `gift_image_…` не создаёт второй push.

События комментариев/реакций записывают уведомление в `users/{uid}/notifications/{id}`. Для E470 участники — автор опубликованного поста и авторы его комментариев, существовавших на сервере к моменту нового комментария. Случайные посетители, будущие участники и сам отправитель не включаются. Отсутствующие/заблокированные/удалённые аккаунты исключаются. Прямой ответ использует существующий `comment-{commentId}`, реакция — существующий `reaction-{postId}-{commentId|post}-{actorUid}`. Прочие участники получают не более одного уведомления обсуждения на пост за 15 минут; повтор сохраняет состояние «прочитано». Удалённый родительский комментарий и непубличный пост не вызывают рассылку.

Заявка дружбы подтверждается существующими `friend_requests` и `friend_requests_sent`: UID из пути совпадают с `fromUid/toUid`, обе записи `pending`, поколение обоих зеркал совпадает с исходным событием. Уже принятая/отменённая заявка не создаёт новый push. Имя и фото берутся из профиля, а не из клиентского текста заявки. Стабильные inbox IDs — `friend-request-{senderUid}` и `friend-accepted-{accepterUid}`; payload остаётся `kind: social`, поэтому текущий клиент открывает страницу друзей.

Принятие требует `acceptedByUid` в **обоих** зеркалах `friends`. Значение — UID принимающего. Trigger обрабатывает только сторону исходного заявителя; противоположное зеркало пропускается. UID, `acceptedByUid` и точный серверный `createTime` зеркал должны совпасть с ожидаемой операцией. Legacy-записи без поля не считаются доказательством принятия. Клиент и фактические rules ещё должны обеспечить этот переход; серверная подготовка сама его не вводит.

Новая региональная встреча рассылается только для `type: групповая`, активного организатора и непустых `country/region`. Получатели выбираются ограниченными страницами по **точному названию страны и региона**, как проверяет текущий `PushTarget`. Организатор, удалённые/заблокированные/незавершённые аккаунты исключаются. Исходные тип, организатор, страна и регион из события сравниваются с текущей записью: удалённая, пересозданная, перенесённая или ставшая личной встреча не рассылается. Перед FCM повторно проверяются встреча, регион получателя и аккаунт. Inbox имеет `type: meeting`, `kind: regional`, `entityId`; push — `kind: new_meeting`, `isChat: false`, `groupId` и серверный `recipientUid`. Личные встречи этот новый trigger никогда не уведомляет.

## Контракт и доверие

POST с `Content-Type: application/json`, `Authorization: Bearer <Firebase ID token>` и единственным допустимым телом:

```json
{"kind":"chat","entityId":"room-id","messageId":"saved-message-id"}
```

Второе значение kind — `group`. JWT проверяется с проверкой отзыва; анонимные аккаунты запрещены. UID должен совпасть с автором **существующего** сообщения, автор должен входить в фактический состав чата/встречи. Сервер сам читает получателей, выключенные уведомления и приватные токены. Входные recipient/token/title/text отклоняются. Ответ не раскрывает число получателей и токенов. События старше 24 часов не рассылаются повторно; возраст берётся из Firestore createTime, а не поля с клиентскими часами. HTTP ограничен 60 запросами/UID/минуту и 3000 запросами/проект/минуту; таймаут ответа — 12 секунд.

FCM data содержит `recipientUid` и **строку JSON** `payload`: для чата `isChat/chatId`, для встречи `isChat/groupId`, для соцуведомления `kind: social`, `notificationId`, `recipientUid`. Приложение должно проверять текущий UID и заново читать сущность/inbox перед показом и открытием — эта проверка реализована в текущем main.dart/PushTarget.

`TOKENS/{uid}` читается только сервером/владельцем. Если одна установка после офлайн-выхода оставила токен на двух аккаунтах, получателем считается только аккаунт с самой новой **серверной** updateTime. Равные timestamps/аномальные дубли отклоняются. Проверка повторяется непосредственно перед FCM. Полностью убрать гонку между последней проверкой и доставкой ОС невозможно: поэтому системный preview содержит только CLRS и общую фразу «У вас новое уведомление», без имени, сообщения или другого личного содержимого. Применяются 23 текущих кода языка; статические Flutter-словари не менялись.

## Дедупликация и границы гарантии

`_push_deliveries/{sha256(event+recipient)}` резервируется транзакцией до FCM, поэтому параллельные HTTP/повторные триггеры не отправляют событие второй раз. Firestore триггеры могут повторяться и приходить не по порядку ([документация Firebase](https://firebase.google.com/docs/functions/firestore-events)). Firestore и FCM не имеют общей транзакции: при неизвестном сетевом результате сохраняется `uncertain`, автоматическая повторная отправка не выполняется, чтобы не дублировать уже доставленный push. При падении процесса после резерва может остаться `sending`; такой push тоже не повторяется автоматически. Уведомление в inbox при этом сохраняется. Это **не гарантия exactly-once доставки**. Ошибка до начала FCM освобождает резерв для безопасного повторения.

Для новых friendship/региональных событий ключ доставки включает `createTime` с секундами и наносекундами. Inbox хранит `sourceCreatedAt`: повтор того же поколения сохраняет `read/createdAt`, новая заявка после отказа или новое принятие после удаления дружбы вновь становятся непрочитанными. Старое событие не обрабатывает пересозданную запись по тому же пути, даже внутри одной миллисекунды; его поколение проверяется в транзакции записи inbox и непосредственно перед FCM. Поле `createdAt` не используется для идентичности: серверный timestamp поля и metadata `createTime` могут иметь разную точность. При первом переходе с legacy inbox без `sourceCreatedAt` текущая подтверждённая операция становится новым поколением.

Региональная выборка читает по 250 профилей и сохраняет checkpoint **после каждого обработанного UID** в серверном `_push_fanouts/{sha256(meetingId+точное createTime)}`. Повтор начинает `startAfter` с сохранённого значения UID, включая случай удаления самого профиля курсора. Ошибка notice/delivery/checkpoint оставляет повторяемую границу: уже завершённая доставка подавляется дедупликацией, необработанный получатель остаётся впереди курсора. `completed` сохраняется вместе с курсором. До отправки и каждого checkpoint транзакционно проверяются текущее поколение, организатор, публичный тип и исходные страна/регион встречи; перенос/удаление/пересоздание останавливают старое событие.

Курсор содержит только ID встречи, `sourceCreatedAt`, последний UID, признак завершения, случайного владельца lease, срок lease/TTL и время обновления. Имена, сообщения, фото и FCM-токены в него не попадают. Lease ограничена 120 секундами; параллельный обработчик получает **retryable 503**, чтобы trigger возобновился после освобождения/истечения lease. Владение проверяется при inbox/резервировании, непосредственно перед FCM и при checkpoint; прежний обработчик не может обновить прогресс или очистить lease нового владельца.

Для регионального пути резерв доставки сначала имеет `reserved` с владельцем lease, затем транзакционно переходит в `sending` перед FCM. После истечения старой lease `reserved` можно безопасно восстановить: старый обработчик уже не может перейти к отправке, а его поздняя ошибка не удаляет новый резерв. Оставшийся `sending` означает неизвестный результат и становится `uncertain`, без повторной отправки. Между отметкой `sending` и вызовом FCM остаётся небольшое окно возможной потери push при аварийном завершении; exactly-once по-прежнему не обещается. Последняя проверка данных и FCM также не атомарны — небольшая гонка изменения региона остаётся; системный preview содержит только общую фразу.

Legacy-профили без явных `country` и `region` исключаются. Read-only сверка основной задачи 28.09.2026 нашла 6095 профилей: оба современных поля заполнены только у 2, поле `city` есть у всех 6095. Поэтому новая региональная рассылка сейчас применима только к современным профилям; страну/регион из произвольного `city` сервер не выводит. Миграция legacy-местоположения этим изменением не выполнялась.

Невалидный токен удаляется только если документ всё ещё содержит именно его; новый токен не затирается. SDK-коды обрабатываются согласно [FCM error codes](https://firebase.google.com/docs/cloud-messaging/error-codes). Таймаут не отменяет уже начатую внешнюю отправку. Логи/ответы не содержат токенов, исходного сообщения и сырых SDK-ошибок.

## Перед любым включением

1. Проверить действующие production rules: клиент не должен читать/писать `_push_deliveries`, `_push_usage` и новый `_push_fanouts`; чужие TOKENS нельзя читать/менять; authorUid/sendByID/membership/likes/status должны быть защищены. Локальный draft rules **не заменяет** существующие production rules. Если любой пересекающийся wildcard разрешает запись, отдельный `allow false` не защищает данные.
   Для трёх новых функций дополнительно нужны: атомарные pending-зеркала дружбы с защищёнными UID; принятие только владельцем входящей заявки и только с одновременным удалением заявки/созданием обоих зеркал; одинаковый `acceptedByUid == request.auth.uid` в обоих зеркалах; запрет произвольного изменения этих документов после создания. Inbox/sourceCreatedAt производит только сервер, получатель меняет только `read`. Создатель встречи совпадает с Auth UID; организатор и публичный/личный тип защищены действующими правилами. Региональная выборка с `country + region + documentId` может требовать действующего индекса; это отдельно сверяется без автоматического создания ресурсов.
2. Настроить серверный `CLRS_PUSH_ENABLED=true` только после проверки. По умолчанию всё выключено. При `FUNCTIONS_EMULATOR=true` отправка FCM принудительно запрещена, допускается только запись локального inbox. `PUSH_SERVICE_ACCOUNT` — необязательное имя отдельного runtime service account; никаких ключей в исходниках или APK.
3. Runtime service account нужны чтение Auth users, чтение соответствующих Firestore документов, транзакционные записи inbox/счётчиков/дедупликации и FCM send. Дать узкие необходимые IAM права, не Owner/Editor. Firestore IAM не ограничивает доступ отдельными document paths; клиентские rules не ограничивают Admin SDK, поэтому доступ runtime account требует отдельной проверки.
4. Лимиты Functions: region europe-west1, minInstances 0, maxInstances 2; HTTP timeout20/concurrency10, triggers timeout120/concurrency1. Бесплатность вызовов/Firestore/Eventarc не гарантируется. При запрете новых платных ресурсов не разворачивать, пока владелец не подтвердит существующий подходящий тариф и бюджет.
5. Если развёртывание отдельно разрешено, выбирать **только конкретно согласованные push-функции из девяти выше** в `firebase.translation.json` / codebase `translation`. Не использовать общий deploy всех exports: пакет также содержит отдельный `translateContent`, который имеет независимые AWS secret bindings. Не разворачивать rules этим шагом. URL успешного `requestPush` можно задать в APK через `CLRS_PUSH_ENDPOINT`; триггеры не требуют этого URL. Новые платные ресурсы остаются запрещены; добавление exports не является разрешением на deploy.
6. Опционально настроить TTL для `_push_deliveries.ttlAt` (30 дней), `_push_usage.ttlAt` и `_push_fanouts.ttlAt` (2 дня). TTL здесь — поле, не уже включённая очистка. Не удалять текущие счётчики/свежие delivery-резервы и курсоры незавершённых свежих событий. Хранение дольше TTL не даёт повторить событие старше 24 часов.

Перед признанием готовности проверить реальный FCM на контролируемых учётных записях: чат/встреча/подарок, comment/reply/reaction, третий участник обсуждения, friend-request→отказ→повтор, принятие только заявителю, новая публичная встреча в точном регионе, отсутствие рассылки личной встречи, смена региона, свернутое/закрытое приложение, muted, offline logout→другой UID, повторный event+HTTP и перезапуск backend. Ни один такой production-сценарий этой локальной проверкой не подтверждён. Прочие push-события в этот набор не добавлены.

Перед включением дружбы клиент должен записывать `acceptedByUid` в обе стороны одной транзакции и прекратить два самостоятельных inbox-write (`sendFriendRequest/acceptFriendRequest`). Выпуск этого перехода согласуется с доступностью безопасных серверных обработчиков: до неё удаление клиентских inbox-write уберёт существующие in-app уведомления. Действующий strict draft нельзя публиковать целиком ради этих новых событий.

Этот клиентский переход уже подготовлен за общим
`CLRS_SERVER_SOCIAL_NOTICES`, **по умолчанию false**. При false прежние inbox
и схема дружбы сохраняются, новых language-write нет. После проверки фактических
rules и согласованного server rollout значение true включает два acceptance
маркера и серверное создание inbox. Под тем же флагом готовый профиль сохраняет
выбранный UI-язык только через `update users/{capturedUid}.language`. Очередь
пропускает устаревший выбор и проверяет текущий/готовый UID, mounted и disposal;
ошибка записи не блокирует вход или локальный выбор языка. `TOKENS.updateTime`
и владение FCM-токеном этой записью не меняются. Static catalogs не изменены.
Клиентские проверки: rollout **19/19**, язык **13/13**. Production APK этой
поставки собран с false, поэтому сам по себе не включает новые серверные функции.
