# Ограниченная серверная очистка удалённой анкеты

Локальная подготовка, 28 сентября 2026. Функция не опубликована и отключена по
умолчанию. Это очистка подтверждённых личных ресурсов, **не полное стирание всех
данных пользователя**. Клиент, платежи и действующие Firebase rules здесь не меняются.

## Условие запуска

`cleanupDeletedProfile` подписывается на настоящий Firebase Auth `onDelete`
через API v1 установленного `firebase-functions`. HTTP endpoint, планировщика и
реакции только на запись `status: deleted` нет. Приложение уже выполняет повторную
проверку пароля, записывает `users/{uid}.status = deleted` и серверный
`deletionRequestedAt`, затем вызывает Auth `user.delete()`
(`lib/service/profile_delete_service.dart`). Неудавшийся Auth delete оставляет
анкету закрытой; очистка не должна запускаться по одной этой отметке.

Нужны одновременно UID/дата создания/время события от Auth, отсутствующий Auth
пользователь с этим UID и существующий tombstone с точным `status: deleted`.
`deletionRequestedAt` должен быть Firestore Timestamp между созданием удалённого
Auth аккаунта и событием удаления. Число, строка, отсутствующая отметка или другой
UID в документе отклоняются. Ошибка чтения Auth не означает отсутствие аккаунта.

По умолчанию `CLRS_ACCOUNT_CLEANUP_ENABLED` не задан: функция возвращает
`disabled` до чтений/записей. Включение требует точного `true`.

## Подтверждённый охват

| Ресурс | Разрешённое действие |
| --- | --- |
| Storage `users/{uid}/photos/` | Удалить старые объекты, включая `thumbs/`; путь подтверждён в profile/edit_profile |
| Storage `profile_images/{uid}/` | Удалить старые объекты регистрации и миниатюры; путь подтверждён в profile_registration_service |
| `users/{uid}/images` | Удалить документы только с `url`/`thumbnailUrl` |
| `users/{uid}/notifications` | Очистить свой inbox только по явному whitelist текущего схемного набора |
| `TOKENS/{uid}` | Удалить только известную схему токенов; если `uid` присутствует, он обязан совпадать |
| `private_users/{uid}` | Удалить только схему `uid`/`email` из локального migration draft, если документ существует |
| `public_profiles/{uid}` | Удалить только проекцию известных публичных полей из локального migration draft |
| `users/{uid}/friend_requests`, `friend_requests_sent` | Удалить свою старую заявку с доказанным UID; зеркало другого пользователя — только с совпадающим UID, pending и одинаковым createdAt, атомарно с собственной записью |
| `users/{uid}` | Удалить только перечисленные ниже личные поля; сохранить сам документ и tombstone |

Whitelist корня: `fullName`, `email`, `profilePic`, `profilePicThumb`, `age`,
`rost`, `about`, `hobbi`, `deti`, `temperament`, `city`, `country`, `countryCode`,
`languageGroup`, `countrySegment`, `region`, `images`, `pol`, `relationStatus`,
`группа`, `group`, `language`, `online`, `lastOnlineTS`, `chatWithId`, `interests`,
`testAnswers`, `profileDetailsSaved`, `isRegistrationEnd`, `registrationNoticePending`.
Список экспортирован в `src/account_cleanup.js`. Поля удаляются update-патчем,
документ не заменяется. `uid`, `status`, `deletionRequestedAt` остаются.

`balance`, gifts, покупки невидимости, платежи, начисления/списания, финансовые
подколлекции и неизвестные поля сохраняются без изменения. Не затрагиваются
сообщения, общие чаты, встречи, посты/комментарии, друзья, чужие уведомления,
wall, grants, аналитические/переводные/push журналы и неизвестные подколлекции.
Не выполняется recursiveDelete и не удаляется весь корень `users/{uid}`.
Схема `users/{uid}/inbox` не обнаружена, поэтому такой путь не выдуман.

## Граница старых фото

Root-задача отдельно провела read-only сверку production: 6470 объектов Storage,
из них 7 под современным `users/{uid}/photos/`, 7 под `profile_images/{uid}/`,
4 под `posts/`, остальные 6452 — legacy/other. Это число объектов **не является
числом фото удаляемого аккаунта**. У трёх проверенных старых профилей фотографии
лежат прямо в корне bucket, UID отсутствует в имени; подтверждённой custom
metadata ownership нет. Эти сведения переданы root-задачей, данный модуль сам
не обращался к production и не перепроверял их. Public/private проекции на этой
read-only выборке отсутствуют; их поддержка выше условна для локальной миграции.

Любая ссылка профиля или image-документа вне двух подтверждённых prefix
отмечается `needsLegacyReview`, `unresolvedPhotoReferences` и статусом
`partial_scope`. Download URL используется только для определения границы
охвата и **никогда как команда удаления**. Неизвестные bucket, hosts, пути или
схемы не становятся разрешёнными объектами. Для дальнейшей сверки серверный
журнал сохраняет до 100 SHA-256 хэшей ссылок без query/fragment; UID добавляется
только внутрь хэша. Ни исходный URL, download token, имя файла, email, имя
человека, ни raw SDK error не записываются в этот журнал/логи. При превышении
лимита сохраняется `photoEvidenceTruncated`.

Хэш подтверждает совпадение уже известного кандидата и не доказывает владение,
не восстанавливает URL и не заменяет защищённую карту соответствия. До включения
на старых профилях нужна отдельно проверенная стратегия legacy ownership и
сохранения минимальных исходных доказательств владельцем данных. Автоматическое
удаление корневых файлов по legacy URL здесь не добавлено. Признак неполноты и
хэши остаются после удаления полей анкеты и повторного запуска; хэши legacy
image-ссылок сохраняются в одной транзакции с удалением исходного документа.

## Повторы, ошибки и повторное создание UID

`_account_cleanup/{sha256(uid + deletionRequestedAt)}` — серверный журнал с
lease, статусом и счётчиками без личного содержимого. Параллельный запуск с
действующей lease возвращает `in_progress`; успешный повтор возвращает
`already_completed`. Auth event wrapper превращает `in_progress` в ошибку:
`failurePolicy` повторяет событие до освобождения/истечения lease, поэтому
падение процесса не приводит к успешному ack единственной оставшейся попытки.
Повтор до истечения lease не запускает вторую очистку. При инфраструктурной ошибке состояние `partial`, lease
снимается и Auth event может повториться. Уже удалённые записи/объекты безопасно
пропускаются; после падения процесса истечение lease позволяет повторить работу.
Firestore/Storage читаются страницами по 100. Abort/deadline проверяется после
медленных чтений и перед следующей операцией; таймер не объявляется отменой уже
начатого SDK-запроса.

Перед каждым удалением проверяются неизменный tombstone, lease и отсутствие
Auth UID. Firestore delete проходит внутри транзакции с прочитанной версией
документа. Документы или фото с create/update time после `deletionRequestedAt`
сохраняются. Timestamp сравнивается с наносекундной точностью. Storage delete
использует `ifGenerationMatch` и `ifMetagenerationMatch` на `bucket.file(...)`,
как требует установленная версия SDK: новая версия файла не удаляется.

Появившийся Auth UID останавливает дальнейшую очистку. Между Auth, Firestore и
Storage общей транзакции нет, поэтому узкое окно между последней Auth проверкой
и удалением полностью устранить этим модулем невозможно. **До подключения
необходимо запретить ручное повторное создание того же UID и повторное
использование его старых ресурсов, пока cleanup выполняется.** Новая обычная
регистрация с новым UID не затрагивается. Без этого организационного/серверного
условия модуль нельзя считать полностью защищённым от privileged UID recreation.

`completed_scope` означает завершение только перечисленных проверенных операций;
`partial_scope` означает оставленные неподтверждённые/новые ресурсы или legacy
фото. Счётчики removed относятся к текущему запуску и не являются общим числом
данных аккаунта. Ни один статус не означает полное стирание всех данных.

## Что нужно для подключения

1. Проверить действующие production schema/rules и точные Storage prefix с
   владельцем. Клиентские rules не должны позволять подделать UID/tombstone,
   писать чужие профили/токены или `_account_cleanup`. При этом rules не ограничивают
   Admin SDK, поэтому runtime IAM нужен отдельный контроль.
2. В `src/index.js` уже добавлен экспорт
   `export { cleanupDeletedProfile } from './account_cleanup_functions.js';`.
   Публиковать только эту функцию после проверки prerequisites; подготовленный
   экспорт сам по себе не развёртывает её и не включает очистку.
3. Выбрать отдельный runtime service account через
   `ACCOUNT_CLEANUP_SERVICE_ACCOUNT`. Нужны только Auth user read, Firestore read,
   transactional update/delete известных записей и журналов, Storage list/get
   metadata/delete в существующем bucket. Runtime не нужны Auth delete/create,
   AWS Translate, FCM send или финансовые API. Не выдавать Owner/Editor и не
   создавать/встраивать сервисные ключи. Firestore IAM не изолирует отдельные
   document paths; возможность удаления финансовых данных технически у Admin
   остаётся, поэтому allowlist кода и отдельный review обязательны. Возможность
   ограничения Storage IAM по prefix должна быть проверена владельцем для
   выбранной политики, а не подразумеваться.
4. Проверить на изолированном Auth/Firestore/Storage Emulator сценарий реального
   удаления и retry, после этого отдельно разрешить деплой. Функция v1 должна
   поддерживаться выбранным runtime/регионом/тарифом проекта. Обработка событий
   может создавать расходы даже при `minInstances: 0`; в текущей подготовке
   никакие ресурсы/деплой/платные вызовы не выполнялись.
5. Включить `CLRS_ACCOUNT_CLEANUP_ENABLED=true` только после этих проверок.
   События, уже полученные при выключенном флаге, завершаются и сами после
   включения не возвращаются. Массовое Auth delete может не порождать отдельные
   lifecycle события для каждого UID: на это нельзя полагаться при последующей
   административной миграции. Backfill endpoint/скрипта этот пакет не содержит.

## Локальная проверка

Целевой прогон: `node --test test/account_cleanup.test.js` в `server/translation`.
Фактический итоговый результат 28 сентября 2026: **19/19 PASS**, 0 fail,
0 skipped, примерно 0,61 с, целевой Node **v22.23.2**. Проверены также
`sourceCreatedAt` в собственном inbox и crash/lease contention/expiry через
Auth wrapper. Облачный runtime этим локальным прогоном не подтверждён.
Тесты используют только in-memory Auth/Firestore/Storage и регистрацию trigger
через установленный SDK с фиктивным projectId; внешних запросов нет. Проверяются
default-off, Auth/tombstone prerequisites, повтор и параллельный повтор, частичная
ошибка, соседний UID, неизменность финансов/общих сущностей, recreated Auth UID,
замена версии фото, транзакционная замена токена, доказательство зеркала заявки,
legacy evidence после повтора, пагинация и прекращение работы после abort.

Отдельная локальная интеграция 28 сентября 2026: **PASS** на Firebase CLI
14.23.0 / Node22.23.2 / Java17.0.12, Auth/Firestore/Storage/Functions Emulators,
проект `demo-clrs-account-cleanup`, только cleanup export и фиктивные данные.
Настоящий Auth delete вызвал onDelete handler: удалены 5 собственных документов
и 2 фото в подтверждённых современных prefix. Уведомление с `sourceCreatedAt`
очищено; tombstone, финансовые/неизвестные поля, платёжные и gift записи,
соседний профиль/фото, общий чат и legacy-файл сохранены.

С действующей lease доставка события вернула HTTP500 и не удалила ресурсы.
После истечения lease **вручную переотправлен тот же настоящий Auth event**:
HTTP200, очистка завершена. Следующая доставка точного дубля вернула HTTP200
без изменений состояния. Это проверка handler и ручной redelivery; **облачное
автоматическое планирование retry, backoff и длительность хранения события
не проверялись**. Серверный handler при этой интеграции не менялся; совпадение
его исходников с протестированной копией закреплено SHA-256 в verification.json.
Unit19 повторно не запускались.

`functions.config()` до handler. Использован официальный адресный фикс
[CLI14.23.0 / PR9401](https://github.com/firebase/firebase-tools/pull/9401),

не включены. Все новые demo-процессы остановлены; прежние эмуляторы на других
портах не затрагивались. Итоговое доказательство:
