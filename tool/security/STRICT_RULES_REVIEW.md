# Строгий локальный набор правил — 28 сентября 2026

**Не публиковать как замену production rules.** Правила действующего Firebase
не получены. Этот набор изолирован от визуальной permissive fixture и доказывает
конкретные разрешённые/запрещённые операции; совместимость всего текущего APK
с ним не заявляется.

## Обязательный блокер текущего APK после 1.0.20+34

Нельзя включать `firestore.strict.rules` целиком, пока клиент читает чужие
`users/{uid}` и сам пишет агрегированные счётчики, inbox, membership и чужой
подарочный инвентарь. Эти операции строгий набор отклоняет; простая публикация
правил сломает профиль/поиск, часть ленты, приглашения и подарки. До включения
нужно подтвердить фактический переход на публичную проекцию профилей,
атомарный перенос legacy email и доверенные операции. Локальная permissive
fixture `tool/local_backend/firestore.rules` также **никогда не подходит для
production**: она разрешает любую запись любому вошедшему пользователю.

`storage.strict.rules` нельзя заменять вслепую: проверены только перечисленные
пути новых фото/ленты/заявок. Неизвестные legacy-пути будут закрыты default deny,
а ранее выданные download-token URLs сохранят действие. Сначала требуется
сверить действующие правила и используемые пути реальных файлов.

## Конкретные несовместимости текущего клиента с безопасными правилами

| Область | Текущее поведение | Что потребуется перед включением strict rules |
|---|---|---|
| Поиск/чужой профиль/друзья | Клиент читает целый `users/{other}`. Старые документы могут содержать email, баланс, gifts и прочие приватные поля | Сверить реальные поля, перенести email атомарно; клиент читает whitelist `public_profiles`, собственное состояние — `users`. Firestore не скрывает поля внутри доступного документа |
| Права администратора | Клиент поддерживает legacy UID allowlist и custom claims | Подтвердить реальных администраторов и выдать серверные `admin` claims; записи `users.role` не дают прав |
| Лайки/комментарии/репосты | `SocialService` транзакцией меняет документ реакции/комментария/стены и чужой агрегированный счётчик | Удалить изменение счётчиков из клиентской транзакции, считать их trusted trigger; строгий тест подтверждает полный отказ legacy comment+counter, без частичного комментария |
| Уведомления | `SocialService.addNotification` пишет в inbox другого UID; часто нет надёжного actorUid/proof, клиент сам задаёт title/body | Trusted trigger на подтверждённое событие; клиент может читать только свой inbox и менять только read |
| Личные чаты | Некоторые старые helpers ищут по `chatId`, без ограничения `user1/user2`; `addChatSecondUser` меняет чужой `users.chats` | Query должен доказывать членство; обновление чужого private профиля вынести на сервер или убрать ненужный legacy индекс |
| Встречи | Создание личного приглашения и вступление включают запись в чужой inbox; membership меняет users напрямую | Trusted membership/invitation operation, либо отдельно доказанные правила на атомарный переход. Сейчас draft блокирует участнику произвольное изменение membership |
| Список встреч | Неограниченное чтение `meets` смешивает коллективные и личные встречи | Раздельные queries: публичные встречи; организатор; приглашённый; участник. Rules не служат фильтром списка |
| Отправка подарка | `shop.dart` читает/меняет sender gifts и чужой presentedGifts, записывает два сообщения и inbox | Существующие финансовые правила и серверная операция требуют отдельной сверки. Draft блокирует клиентский инвентарь; платёжный код этим заданием не менялся |
| Невидимка/удаление профиля | Клиент меняет оплаченные flags/end/status в приватном профиле | Серверная операция с проверкой срока/владельца; не разрешать произвольную клиентскую оплату/статус ради прохождения теста |
| Фото | Profile paths существующие; правила проверяют владельца/размер/MIME | Проверка bytes на реальное изображение и антивирус/модерация — отдельная серверная задача; MIME сам по себе не доказывает содержимое |

Уже выданные Firebase Storage download URLs с `token=` действуют как bearer
ссылки. Проверенный запрет прямого чтения без авторизации не отменяет эти URL.
Перед ужесточением приватности вложений нужна инвентаризация и политика
перевыпуска токенов; в этом задании действующие файлы/токены не менялись.

## Offline migration plan

`plan_private_profile_migration.py` читает сохранённый REST-format snapshot
`{"documents":[{"name":...,"fields":...,"updateTime":...}]}` и создаёт только
review plan. Сеть/SDK/учётные данные не используются; writes не исполняются.
Выход содержит персональные данные, создаётся с правами 0600 и не должен
попадать в git/ZIP/логи. Существующий файл не перезаписывается.

```sh
python3 tool/security/plan_private_profile_migration.py \
  --input /private/location/users-snapshot.json \
  --output /private/location/profile-migration-review.json
```

Перед реальным применением требуется сверить текущие rules/схему, свежий
резервный снимок, порядок переключения клиента и серверных операций. Для
невидимых/удалённых/заблокированных профилей план удаляет публичную проекцию;
приватный оригинал сохраняется. Отдельный backup/rollback реальных данных
не выполнялся и готовность production не подтверждена.
